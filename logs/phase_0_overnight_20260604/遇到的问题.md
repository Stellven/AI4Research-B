# 遇到的问题

本文档记录 SkillGen Phase 0 修复和 overnight run 过程中实际遇到的问题、造成的影响、已经采用的解决办法，以及仍然需要后续 agent 处理的部分。

## 1. `blocked` / `not_testable` / `ready` / `reproduced` 语义混在一起

### 问题

早期 research validation report 里同一个 claim 的状态既承担“claim 是否被验证成功”的含义，又承担“下一步是否可以执行”的含义。

这导致一个 claim 可能因为缺少数据、缺少 runner、缺少 adapter 而显示 `blocked`，但又在其他地方显示为“ready for execution”。用户很难判断：

- 这个 claim 到底有没有被验证成功；
- 只是执行前置条件 ready，还是结果已经支持论文；
- `blocked` 是缺人类批准、缺数据、缺脚本，还是只是还没跑。

### 影响

- 报告读起来像有很多 claim statuses，但主 claim 并没有真正被 reproduced。
- `blocked` 和 `not_testable` 的边界不清。
- 很容易把“计划 ready”误读成“验证成功”。

### 已采取解决办法

把状态拆成两层：

- `claim_verdict_status`：只表示 claim 的验证结论，例如 `reproduced`、`partially_reproduced`、`not_reproduced`、`blocked`。
- `execution_readiness_status`：只表示执行准备状态，例如 `ready_for_execution`、`partially_ready_full_matrix`、`ready_for_reconstructed_baseline_comparison`。

为了兼容旧 artifact，`status` 仍保留为 `claim_verdict_status` 的 alias。

### 剩余风险 / 下一步

后续 agent 更新 claim matrix 时，必须继续遵守这个分层：

- 不能因为某个 benchmark “ready” 就把 claim 改成 `partially_reproduced`。
- 只有执行结果支持 claim，才可以改变 `claim_verdict_status`。

## 2. “full matrix run”被误解成已经可以一键跑完 80 条

### 问题

当前已有 full matrix contract 和命令模板，但并没有成熟的一键 full matrix runner。

论文 Table 1 的 full matrix 是：

```text
10 个 benchmark rows × 8 个 paper models = 80 entries
```

目前实际 overnight 只完成了 1 个 entry：

```text
mcp_bench_single::openai/gpt-5.4-nano
```

### 影响

- “准备 full matrix run”和“完成 full matrix run”容易混淆。
- 单条 entry 的结果不能代表 aggregate Table 1 claim。
- 1/80 negative entry 不能把 aggregate claims 推进到 `partially_reproduced`。

### 已采取解决办法

新增独立 observed-entry artifact：

- `phase_0/runs/skillgen_phase0_thorough_20260602/artifacts/08_results/full_matrix/observed_entries.json`
- `phase_0/runs/skillgen_phase0_thorough_20260602/artifacts/08_results/full_matrix/observed_entries.md`

该 artifact 明确记录：

- 只观察到 1/80 entries；
- 使用的是 reconstructed low-cost config；
- 该 entry 是 `not_reproduced`；
- aggregate Table 1 claims 仍保持 `blocked`。

### 剩余风险 / 下一步

C 组需要补真正的 full matrix runner：

- 自动生成 per-target/per-model config；
- 按 entry 执行 train/eval；
- 保存 stdout/stderr、run artifacts、token usage、per-instance trajectories；
- 聚合 80 entries；
- 只有聚合结果完整后，才能更新 Table 1 aggregate claims。

## 3. ALFWorld 不是直接可跑状态

### 问题

ALFWorld 是开源 benchmark，但当前 SkillGen run 里没有现成的 SkillGen-compatible train/test JSON。

缺少的不只是“下载数据”，还包括：

- canonical ALFWorld 数据来源确认；
- 论文 IOD/OOD split 定义；
- ALFWorld trajectory/task 到 SkillGen `TaskInstance` 的 adapter；
- 生成 `alfworld_iod` 和 `alfworld_ood` 的 train/test JSON；
- split/provenance manifest；
- reconstructed execution deviation note。

### 影响

ALFWorld IOD/OOD 占 Table 1 的 16 条 entries：

```text
2 个 ALFWorld rows × 8 个 models = 16 entries
```

这 16 条在 adapter 完成前不能进入真实 full matrix execution。

同时 cross-model transfer claim 也依赖 ALFWorld OOD，因此会被继续卡住。

### 已采取解决办法

已明确分组：

- A 组负责 ALFWorld adapter。
- C 组只在 A 组交付 SkillGen-compatible JSON 后负责 full matrix execution。
- F 组如果处理 transfer claim，只消费 A 组产出的 ALFWorld OOD 数据。

### 剩余风险 / 下一步

A 组至少需要交付：

- `data/alfworld_iod/train.json`
- `data/alfworld_iod/test.json`
- `data/alfworld_ood/train.json`
- `data/alfworld_ood/test.json`
- adapter script
- split/provenance manifest
- deviation note
- smoke run logs

## 4. OpenRouter 账户无法继续付费调用

### 问题

overnight 第一次运行 `mcp_bench_single` 时，官方代码默认走 OpenRouter。

运行在 induction 阶段失败，stderr 显示：

```text
OpenRouter HTTP 402 insufficient credits
```

### 影响

- OpenRouter 路径不能继续执行。
- 非 OpenAI provider routes 不能直接通过当前 fallback 解决。
- 多模型 full matrix 的 8 个 paper model 里，只有 `openai/...` 路径被确认可用 direct OpenAI fallback。

### 已采取解决办法

检查官方代码发现 `llm.py` 支持：

```text
SKILLGEN_DIRECT_OPENAI_FOR_OPENAI_MODELS=1
```

该环境变量会让 `openai/...` route 绕过 OpenRouter，直接使用 `OPENAI_API_KEY`。

随后做了最小 probe：

```text
llm.chat("Return OK only.", model="openai/gpt-5.4-nano")
```

结果返回 `OK`，证明 direct OpenAI route 可用。

之后补充了 provider resolution artifact 和 runner policy：

- `phase_0/runs/skillgen_phase0_thorough_20260602/artifacts/provider_resolution_status.json`
- `phase_0/runs/skillgen_phase0_thorough_20260602/artifacts/provider_resolution_status.md`
- `phase_0/runs/skillgen_phase0_thorough_20260602/artifacts/06_plans_and_contracts/provider_resolution_status.json`
- `phase_0/runs/skillgen_phase0_thorough_20260602/artifacts/06_plans_and_contracts/provider_resolution_status.md`

该 artifact 只记录 key 是否存在，不记录 secret 值。当前结论是：

- `OPENROUTER_API_KEY` 存在，但已有 OpenRouter 402 insufficient-credit 证据；
- `OPENAI_API_KEY` 存在，`openai/...` routes 可以通过 direct OpenAI fallback 继续执行；
- `ANTHROPIC_API_KEY`、`GOOGLE_API_KEY`、`GEMINI_API_KEY`、`MISTRAL_API_KEY`、`XAI_API_KEY`、`GROQ_API_KEY`、`TOGETHER_API_KEY`、`FIREWORKS_API_KEY`、`DEEPINFRA_API_KEY` 当前未检测到；
- 当前 runner 不具备非 OpenAI 模型的 direct-provider integration，因此非 OpenAI paper routes 仍依赖 OpenRouter 聚合路由。

同时更新 full-matrix runner：

- 默认继续选择 `openai/...` entries；
- 对非 OpenAI entries 写入 `provider_unavailable`，原因是 `provider_unavailable_openrouter_402`；
- `provider_unavailable` 不等同于 benchmark 失败，也不等同于 claim 的 `not_reproduced`，它只表示当前 provider 路径不可执行；
- 不允许把非 OpenAI paper models 自动替换成 OpenAI models 来冒充 Table 1 reproduction。

一次 dry-run 已确认当前状态：

```text
provider_resolution_status = openai_ready_non_openai_provider_unavailable
openai_candidate_ready_models = 2
non_openai_provider_unavailable_models = 6
provider_unavailable entries = 60
```

### 剩余风险 / 下一步

- OpenAI models 可以继续用 direct OpenAI fallback 跑。
- 非 OpenAI models 仍需要：
  - 修复 OpenRouter billing；
  - 或补充并实现各模型的可用 direct provider/API route；
  - 或在 deviation note 中明确改用可执行 substitute model，但这只能作为扩展/偏离实验，不能当作原 Table 1 的对应模型复现。

## 5. `main.py --resume` 不能复用只有 trajectory JSONL 的失败 run

### 问题

第一次 `mcp_bench_single` 失败前已经生成 baseline trajectories，但没有写出 `checkpoint.json`。

尝试：

```text
main.py --resume <run_dir>
```

失败，原因是官方 pipeline 的 `--resume` 要求 run dir 内有有效 checkpoint。

### 影响

虽然 baseline trajectory JSONL 存在，但不能直接恢复训练。

只能重新 fresh run，导致重复 baseline API 成本。

### 已采取解决办法

将失败和 resume failure 都留档：

- `train_stdout.txt`
- `train_stderr.txt`
- `train_resume_stdout.txt`
- `train_resume_stderr.txt`

然后用 direct OpenAI fallback 做 fresh run。

### 剩余风险 / 下一步

如果要节约后续成本，可以考虑补一个受控 runner：

- 当只有 `baseline_trajectories.jsonl` 时，允许把它转换成合法 checkpoint；
- 或者直接进入 induction 阶段；
- 但这属于修改 official execution behavior，必须写 deviation note。

## 6. 单个 full-matrix entry 成本和耗时都不小

### 问题

即便使用 low-cost reconstructed config，`mcp_bench_single::openai/gpt-5.4-nano` 仍消耗：

- training token usage: `446895`
- eval token usage: `110982`
- combined: `557877`

### 影响

如果线性外推，80 entries 会非常贵，并且耗时很长。

同时不同 benchmark 和不同模型的成本不均匀，不能简单按 1 条 entry 外推。

### 已采取解决办法

先只跑 1 个低风险小 entry，验证：

- config 路径可用；
- official `main.py` 可执行；
- official `eval_skill.py` 可执行；
- trajectory retention 可用；
- result artifact 可写出。

### 剩余风险 / 下一步

批量 full matrix 前，C 组需要做执行预算表：

- 每个 target 的 train/test size；
- 每个 model route；
- expected token/cost range；
- 并发策略；
- failure retry policy；
- per-round trace retention policy。

## 7. 新跑出的 entry 是负向证据，不能推进 claim

### 问题

`mcp_bench_single::openai/gpt-5.4-nano` 训练完成后，construction-time verification 结果是：

```text
paired_n=4
baseline_acc=0.75
skill_acc=0.25
repair=0
regression=2
net_gain=-2
passed=false
```

官方代码因此把 skill 标为 `DEPRECATED`。

held-out eval 结果是：

```text
n=16
baseline_acc=0.8125
skill_acc=0.8125
delta_acc=0.0
net_gain=0
skill_rejected=true
```

### 影响

这是 entry-level `not_reproduced`，不能作为 `partially_reproduced` 证据。

### 已采取解决办法

将结果记录为 negative evidence：

- 不修改 aggregate Table 1 claims；
- 不把 blocked/not_testable 推进为 partial；
- 写入 `observed_entries.json` 和 research validation report addendum。

### 剩余风险 / 下一步

后续 full matrix runner 应继续接受负向结果作为有效 evidence。

Phase 0 的目标不是强行变成 reproduced，而是准确记录是否 reproduced。

## 8. D 组 baseline comparison 已 ready，但还没有实际跑 baseline adapters

### 问题

D 组解决的是 baseline generator comparison。

已经完成：

- baseline source identity review；
- license evidence exception；
- adapter deviation approval；
- four baseline repos fetched and pinned。

但还没有实际把 Trace2Skill / SkillX / EvoSkill / CoEvoSkills 转成可执行 single-skill comparison runner。

### 影响

`claim_baseline_generator_comparison` 仍然是：

```text
claim_verdict_status = blocked
execution_readiness_status = ready_for_reconstructed_baseline_comparison
```

也就是说“准备可以开始做 reconstructed baseline comparison”，不是“已经复现”。

### 已采取解决办法

把 source/license/adapter approval 和 deviation note 都写成 artifact。

### 剩余风险 / 下一步

D 组下一步要实现并运行 baseline adapters。

完成之前，不能把 baseline comparison claim 改成 partial。

## 9. LiveCodeBench 是另一个 benchmark 问题，不是 ALFWorld adapter 能一起解决

### 问题

LiveCodeBench 是 open/reconstructed split 问题，和 ALFWorld adapter 是两个独立 benchmark line。

### 影响

ALFWorld adapter 完成后，不能自动解决 LiveCodeBench。

### 已采取解决办法

B 组负责 LiveCodeBench source/split contract。

### 剩余风险 / 下一步

B 组需要确保：

- release/version source 清楚；
- train/test split 可复现；
- generated split manifest 可审计；
- SkillGen JSON 格式可被 `main.py` 和 `eval_skill.py` 加载。

## 10. per-round traces 必须从下一次大规模 run 开始强制保留

### 问题

Figure 7 / refinement claim 依赖完整 per-round traces。

只有最终 eval result 不够，还需要看到每一轮 refinement 的：

- candidate skill；
- verification sample；
- baseline/with-skill trajectories；
- repair/regression/net gain；
- gate 是否通过；
- deprecated skill 的原因。

### 影响

没有 per-round traces，就无法验证 refinement / best-of-k / Figure 7 类 claim。

### 已采取解决办法

已经加入备注：下一次 run 必须保留所有 per-round traces。

官方 `eval_skill.py` 默认保存 trajectories；训练 run 也会保存 verification round artifacts。

### 剩余风险 / 下一步

full matrix runner 必须显式检查这些文件存在：

- `verification/round_*/verification_baseline.jsonl`
- `verification/round_*/verification_with_skill.jsonl`
- `verification/round_*/verification_summary.json`
- `checkpoint_trajectories.jsonl`
- held-out `eval_results_trajectories/*.jsonl`

## 11. Artifact 有顶层副本和 categorized mirror，容易不同步

### 问题

run artifacts 里很多文件既存在于：

```text
artifacts/<file>
```

也存在于：

```text
artifacts/<category>/<file>
```

例如 research validation report 同时有：

```text
artifacts/research_validation_report.md
artifacts/00_run_summary/research_validation_report.md
```

### 影响

如果只更新其中一份，后续 agent 可能读到旧结论。

### 已采取解决办法

overnight addendum 同步更新了两份 research validation report。

### 剩余风险 / 下一步

后续更新 artifact 时，要么使用 automation 的 mirror write helper，要么手动同步顶层和 categorized mirror。

## 12. 现有 positive evidence 仍主要是 smoke / reduced POC scale

### 问题

目前真正 positive 的 evidence 主要包括：

- AIME construction-time smoke positive；
- ScienceWorld token smoke positive；
- auditable skill artifact smoke evidence；
- token logging mechanics partial evidence。

这些不是 full paper-scale reproduction。

### 影响

可以支持 `partially_reproduced`，但不能支持 `reproduced`。

### 已采取解决办法

report 中保持这些 claim 为 `partially_reproduced`，并明确 scope 是 smoke/reduced POC scale。

### 剩余风险 / 下一步

如果老板要求“不能有不能 verify 的 claim”，下一步不是直接改 label，而是：

- 找到可执行 verification route；
- 标注 reconstructed deviation；
- 跑出 evidence；
- 再决定是否能变成 partial。

## 当前建议的后续执行顺序

1. A 组完成 ALFWorld adapter。
2. C 组补 full matrix runner。
3. C 组先跑 direct OpenAI 的 ready rows，例如 `mcp_bench_all`、`socialmaze_fts`、`socialmaze_upi`。
4. B 组确认 LiveCodeBench split/source 后交给 C 组。
5. D 组实现 baseline adapters 并运行 reconstructed baseline comparison。
6. F 组等 ALFWorld OOD 和 full matrix traces 后再推进 transfer claim。
7. 每次 run 后只根据 executed evidence 更新 `claim_verdict_status`。
