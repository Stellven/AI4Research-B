# Phase 0 Pipeline Presentation Skeleton

Status: presentation draft  
Purpose: introduce the Phase 0 research-validation workflow

## One Sentence

Phase 0 checks whether a paper's official code can reproduce the paper's own benchmark claim, and preserves enough evidence for a human to audit the conclusion.

## What Phase 0 Is

```text
paper/report + official code
  -> benchmark claim
  -> approved commands
  -> official run evidence
  -> paper-vs-observed comparison
  -> validation report
```

Phase 0 is not a paper summary and not a reimplementation. The evidence must come from official code, official commands, captured logs, generated result files, and explicit comparison to the paper.

## Success Standard

A successful Phase 0 package lets a reviewer answer:

- What claim was tested?
- What official code and commands were used?
- What environment and resources were required?
- What raw logs and result files were produced?
- Did the observed result match the paper's metric, split, and aggregation?
- What is reproduced, blocked, failed, or not testable?

## Workflow Table

| # | Step | What Happens | Module / Tool | Main Artifact | Gate / Error Handling |
| --- | --- | --- | --- | --- | --- |
| 1 | Intake | Register paper/report, code source, budgets, and constraints. | CLI, Orchestrator, Artifact Store | `input_manifest.json` | Missing paper/code blocks the run or marks `out_of_scope`. |
| 2 | Research Parse | Extract paper text, tables, code links, claims, metrics, datasets, and splits. | Research Parser, PDF/text tools, optional LLM helper | `paper_parse.md`, `paper_parse.json` | Parse failure is recorded and marked `not_testable`. |
| 3 | Claim Extraction | Choose benchmarkable claims and convert them into validation targets. | Claim Extractor, Benchmark Contract Writer | `claims.json`, `benchmark_claims.json` | Vague or non-measurable claims stop at review or become `not_testable`. |
| 4 | Human Claim Review | Human confirms the target claim, metric, dataset, split, and paper value. | Review Gate | `human_claim_review.md` | Human can accept, revise, reject, or request another claim. |
| 5 | Code Intake | Copy or clone official code and record source URL, commit, branch, files, and README. | Code Intake, Git/local file tools | `code_manifest.json`, `repo_snapshot.md`, `code/official/` | Missing or unofficial code blocks exact reproduction. |
| 6 | Instruction Extraction | Extract official install and benchmark commands from README, scripts, docs, and appendix. | Instruction Extractor, Skill Safety Checker | `official_instructions.md`, `command_plan.json` | Ambiguous or risky commands wait for human command review. |
| 7 | Environment Planning | Record dependencies, package manager, GPU/network/API/Docker needs, file writes, and cost. | Environment Runner, Safety Checker | `environment_plan.md`, `environment.json` | High-risk or expensive setup is blocked until approved. |
| 8 | Command Review | Human reviews install/benchmark commands before third-party code runs. | Review Gate | `human_command_review.md`, `approval.json` | Reject or revise unsafe commands; do not silently patch official code. |
| 9 | Install And Benchmark | Run approved official install and benchmark commands. Capture stdout, stderr, exit code, runtime, and output files. | Environment Runner, Benchmark Runner, shell tools | `outputs/*.txt`, `raw_benchmark_outputs/` | Nonzero exit preserves logs and marks `failed_to_run` or `blocked`. |
| 10 | Result Parsing | Extract observed metrics from result files first, logs second. | Result Parser | `benchmark_results.json`, `benchmark_results.md` | If no metric can be parsed, mark `not_testable`; do not guess values. |
| 11 | Claim Comparison | Compare observed result to paper result using the same metric, split, config, and aggregation where possible. | Claim Comparator | `claim_comparison.json`, `claim_comparison.md` | Mismatched metric/split/aggregation prevents exact reproduction claims. |
| 12 | Human Result Review | Human inspects parsed results and comparison before final conclusion. | Review Gate | `human_result_review.md` | Human can accept, revise, or reject the interpretation. |
| 13 | Validation Report | Write the final evidence-backed status and limitations. | Research Validation Reporter | `research_validation_report.md` | Report must link to claims, commands, logs, parsed results, and comparison. |
| 14 | Optional Extension | Run extra benchmarks only after official reproduction is attempted. | Benchmark Runner, Reporter | extension-specific results | Extended results must not change original-paper reproduction status. |

## Status Labels

| Status | Meaning |
| --- | --- |
| `reproduced` | Observed result matches the paper claim within the accepted comparison rule. |
| `partially_reproduced` | Some evidence supports the claim, but scope or setup is incomplete. |
| `not_reproduced` | Official code runs, but observed results contradict or fall short of the claim. |
| `not_testable` | Required metric, data, split, weights, scripts, or instructions are missing or unclear. |
| `failed_to_run` | Approved install or benchmark command failed and logs were preserved. |
| `blocked` | Human input, credentials, hardware, network, budget, or external resources are required. |
| `out_of_scope` | The paper is outside Phase 0 scope or has no official runnable code. |

## Artifact Layout

Generated evidence is split by generation date:

```text
phase_0/runs/<yyyymmdd>/
  input/
  artifacts/
  outputs/
  integration/
  playback/
  code/official/
```

Rules:

- Generated artifacts, logs, playback, and integration records belong under the date they were generated.
- Original paper inputs may stay under the intake date.
- `code/official/` stays intact as a runnable checkout; do not split source code by file timestamp.
- Append-only JSONL logs are split by record timestamp if they span multiple dates.

## Quality Gates

Phase 0 stays lightweight by using cheap checks after each artifact write and four formal human gates:

| Gate | Question |
| --- | --- |
| Claim gate | Are we testing the right paper claim with the paper's original metric? |
| Command gate | Are the official commands safe, affordable, and approved to run? |
| Result gate | Do parsed results match raw logs and generated files? |
| Final gate | Does the report conclusion follow from the evidence? |

## Presentation Close

The key idea is traceability: every conclusion should point back to a paper claim, official code, approved command, raw log, parsed metric, and comparison artifact. If any link is missing, Phase 0 should say `blocked`, `failed_to_run`, or `not_testable` instead of pretending the paper was reproduced.
